# 一、全双工交互到底意味着什么

在讲架构之前，先澄清一个概念。传统 AI 交互是**半双工**的，像对讲机：

```
用户说话 → 等说完 → VAD 检测结束 → 编码整段输入 → LLM 推理 → 输出完整回复 → 下一轮
```

这导致几个问题：

- 你说到一半，它只能干等着
- 它在说话时，听不见你的新指令
- 整个交互是"回合制"的，有明确的时空割裂

而 MiniCPM-o 4.5 的**全双工**目标是：**模型持续在看、在听、在想、在说，四件事并行发生。**

这不是简单的"边说边听"，而是模型内部有一个持续刷新的"世界观"，能自主决定什么时候介入、说什么、怎么被打断。

# 三、Omni-Flow 时间片：多模态对齐的核心

这是最容易被误解的部分。Omni-Flow 的"时间片"**不是操作系统层面的线程调度**，而是**多模态数据的逻辑对齐窗口**。

## 3.1 不同模态的天然节拍不同

三个模态的原始产出速率差异巨大：

| 模态 | 原始采集率 | 编码器输出 |
|------|-----------|-----------|
| 视频 | 30 fps（每 33ms 一帧） | SigLIP 每帧输出 visual tokens |
| 音频 | 16kHz 采样 | Whisper 每 300ms 输出 audio tokens |
| LLM | — | 每 forward 一次约 50-100ms |

它们不可能"同时 ready"。所以 Omni-Flow 采用策略是：**就近打包 + 时间戳标注**，而不是硬等所有模态对齐。

## 3.2 一个时间片的具体例子

假设系统设置一个**逻辑时间片 Δt = 200ms**。

在物理时间线上：

```
时间(ms):    0    33   66   100  133  166  200  233  266  300  333  366  400
             │    │    │    │    │    │    │    │    │    │    │    │    │
视频帧:      F0   F1   F2   F3   F4   F5   F6   F7   F8   F9   F10  F11  F12
             └───────────┘    └───────────┘    └───────────┘    └───────────┘
             时间片0 (0-200)   时间片1 (200-400)  时间片2 ...

音频输出:     A0─────────────►A1─────────────►A2─────────────►
              (0-300ms窗口)   (300-600ms窗口)
```

注意音频 Whisper 可能是按 300ms 窗口处理的，而视频打包是 200ms 边界。两者并不同步。

**打包器在 t=200ms 时做什么？**

它检查三个模态缓冲区，把**当前已 ready 的最新数据**封装成一个"感知包"（Perception Packet）：

```
Packet_0 = {
    timestamp: 200,                // 时间片边界
    video_tokens: [F0, F1, F2, F3, F4, F5],   // 6 帧视频
    audio_tokens: A0_partial,      // A0 中已解码的部分（到 200ms 为止）
    prev_text: "",                 // 之前 LLM 生成的文本
}
```

**核心逻辑**：不是等所有模态凑齐，而是取边界前最新可用的数据。

## 3.3 模态对齐缓冲区

每个模态有独立的队列，打包器定期消费：

```
┌─────────────────────────────────────────┐
│           模态对齐缓冲区                  │
├──────────────┬──────────────┬───────────┤
│  视频队列     │  音频队列     │  文本队列  │
│  (SigLIP产出)│ (Whisper产出)│ (LLM产出) │
├──────────────┼──────────────┼───────────┤
│  F0@0ms      │  A0_chunk0   │           │
│  F1@33ms     │  A0_chunk1   │           │
│  F2@66ms     │  A0_chunk2   │           │
│  F3@100ms    │              │           │
│  F4@133ms    │              │           │
│  F5@166ms    │              │           │
└──────────────┴──────────────┴───────────┘
         │              │            │
         └──────────────┴────────────┘
                        ▼
                 ┌─────────────┐
                 │   打包器     │
                 │  @200ms边界  │
                 └─────────────┘
```

这个设计让各编码器可以按自己的最优频率运行，不必互相等待。

## 3.4 LLM 推理是异步的

很多人误以为"每 200ms 触发一次 LLM forward"。实际上：

```
时间片 0-200ms:    打包器产出 Packet_0
时间片 200-400ms:  打包器产出 Packet_1（同时 LLM 在处理 Packet_0）
时间片 400-600ms:  打包器产出 Packet_2（同时 LLM 在处理 Packet_1）
```

LLM 推理线程是**独立消费**打包器产出的队列。只要 GPU 算力够，它可以比打包频率更快；如果负载高，它也可以慢慢追。

**Omni-Flow 的"高频刷新"本质**：不是严格按时间片同步调度，而是利用 KV Cache 复用，让每个新 Packet 的推理成本极低。

# 四、KV Cache 的流式管理策略

这是支撑全双工性能的核心工程问题。在持续运行的流式场景下，KV Cache 不能无限增长，也不能每次从头计算。

## 4.1 KV Cache 的增长模式

传统 Chat 中，KV Cache 按**对话轮次**增长：

```
用户: "今天天气怎样？"  → KV[0:10]
助手: "今天晴天"       → KV[10:14]
用户: "明天呢？"       → KV[14:18]
```

在 Omni-Flow 中，没有"轮次"，只有**高频增量包**：

```
时间片0: 视频[F0-F5] + 音频[A0] → 500 tokens → KV[0:500]
时间片1: 视频[F6-F11] + 音频[A1] + 文本"今天" → 20 tokens → KV[500:520]
时间片2: 视频[F12-F17] + 音频[A2] + 文本"天气" → 20 tokens → KV[520:540]
```

每次新时间片进来，只需要计算**新增 token**的 KV，前面的直接复用。

## 4.2 追加式更新（Append-Only）

正常流式下的伪代码逻辑：

```
初始化: kv_cache = [系统提示 tokens]

时间片0:
  输入 = Packet_0 编码后的 tokens
  新_kv = model.forward(输入, past_kv=kv_cache)
  kv_cache = concat(kv_cache, 新_kv)

时间片1:
  输入 = Packet_1 编码后的 tokens
  新_kv = model.forward(输入, past_kv=kv_cache)
  kv_cache = concat(kv_cache, 新_kv)

时间片2:
  ...
```

由于 Qwen3-8B 使用 GQA（Grouped Query Attention），每新增一个 token 的 KV 显存开销是固定的。这让高频增量更新成为可能。

## 4.3 显存上限与滑动窗口

流式运行 10 分钟后，如果全部保留：

- 视频 30fps，每帧 64 tokens → 每分钟 11.5 万 tokens
- 音频、文本叠加 → 总量迅速突破显存上限

所以必须有**丢弃策略**。最合理的推断是**模态感知的分层保留**：

| 模态 | 保留策略 | 原因 |
|------|---------|------|
| 视觉（视频帧） | 时间滑窗，只保留最近 N 秒 | 相邻帧冗余度 95%+ |
| 音频 | 时间滑窗，保留最近 10-30 秒 | 语音短期依赖性强 |
| 文本（LLM 生成） | 尽量全保留，或摘要压缩 | 对话核心，token 数量少 |

**滑动窗口的实现不是删除 KV Cache 中间一段**（会导致位置编码断裂），而是：

- 定期丢弃最早的视频帧 KV
- 必要时对旧文本做**显式摘要**：让模型生成压缩文本，丢弃对应 KV，用摘要重新编码

## 4.4 打断场景下的 KV Cache 处理

全双工最 tricky 的部分是**打断**。当用户插话时，系统怎么处理已经生成一半的 KV？

**软打断**（话题连贯，只是纠正）：

```
AI 正在生成: "明天的天气也是晴天，适合..."
用户打断: "我是问北京的天气！"

处理: 保留全部 KV，直接追加用户新输入
结果: LLM 看到上下文后自然修正
```

Attention 机制会让新输入的 token 去关注相关历史，弱化之前生成的错误内容。

**硬打断**（话题切换或命令式打断）：

```
AI 正在生成: "番茄炒蛋第一步是..."
用户打断: "停！换个小鸡炖蘑菇！"

处理: 截断 AI 生成文本的 KV，回滚到上一次用户输入边界
保留: 感知部分的 KV（视频里用户换了食材，这个信息仍然有效）

截断前: [系统提示, ..., 感知, "番茄", "炒蛋", "第一步", "是"]
截断后: [系统提示, ..., 感知] + [新用户指令]
              ↑
        保留环境感知
```

这要求系统维护一个**用户输入边界索引表**，用于打断时快速定位回滚点。

## 4.5 端侧显存精打细算

文章说 RTX 5070（12GB）能跑全双工。我们来算笔账：

```
Qwen3-8B INT4 量化后:
  模型权重: ~4GB
  激活值/临时buffer: ~1GB
  留给 KV Cache: ~6-7GB

假设 INT4 KV Cache:
  每 token 约 8-16KB
  7GB 可用显存 ≈ 45 万 tokens 的理论上限

实际有效上下文: 控制在 8K-32K tokens 之间
（考虑碎片、多模态开销、语音解码器等）
```

这意味着视觉 token 必须被**高度压缩**。文章提到"高压缩率"，可能的手段：

- 每帧视频 token 数远小于 64（通过时序池化）
- 相邻相似帧合并或丢弃
- 只取关键帧保留

## 4.6 完整的 KV 管理流程

```
新时间片 Packet_t 到达
        │
        ▼
┌─────────────────────────┐
│ 1. 编码新感知数据        │
│    视频 → SigLIP         │
│    音频 → Whisper        │
└──────────┬──────────────┘
           ▼
┌─────────────────────────┐
│ 2. 判断打断状态          │
│    用户是否在说话？       │
└──────────┬──────────────┘
           │
    ┌──────┴──────┐
    ▼             ▼
  软打断        硬打断 / 正常流式
    │             │
    ▼             ▼
┌─────────┐   ┌─────────────────────┐
│ 保留全部 │   │ 截断生成文本部分     │
│ KV，追加 │   │ 的 KV（回滚到上一    │
│ 新输入   │   │ 轮用户输入边界）      │
└────┬────┘   └──────────┬──────────┘
     │                    │
     └─────────┬──────────┘
               ▼
     ┌─────────────────────┐
     │ 3. 检查显存上限      │
     │    当前长度 > 阈值？ │
     └──────────┬──────────┘
                │
         ┌──────┴──────┐
         ▼             ▼
       未超限        即将超限
         │             │
         ▼             ▼
     ┌─────────┐   ┌─────────────────────┐
     │ 直接追加 │   │ 触发压缩策略         │

                   └─────────────────────┘
```

# 五、TAIL 语音方案：流式生成的时序艺术

文章提到语音合成用了 **TAIL（Time-Aligned Interleaving）** 方案。这是一个特别精巧的设计，解决的是一对矛盾：

- **连贯性需要预读**：知道后面几个字，发音才自然
- **实时性不能抢跑**：用户刚说完，AI 就要立刻回应

传统流式 TTS 的问题：

```
文本: "今天 天气 很好"
传统合成:  需要看到整句后才开始 → 延迟大
          "今天天气很好" → ♪今天天气很好♪（一次性输出）

TAIL 方案: 每个语音块紧跟最新文本
文本流:    "今天" → "天气" → "很" → "好"
语音流:    ♪今♪  → ♪天♪  → ♪气♪  → ♪很♪  → ♪好♪
               ↑
         轻量级预读解决跨词连贯性
```

这让语音输出能**紧跟文本流**，在全双工场景下支持即时打断——用户一插嘴，AI 的语音输出可以立刻截断，不会滞后好几秒。

# 六、Omni-Flow 与传统架构的本质区别

用一张对比图总结：

```
传统多模态（回合制）:
┌─────────────────────────────────────────────────────────────┐
│  用户说完一段话(5s)                                         │
│     └──► VAD检测结束                                        │
│            └──► 编码整段视频 + 整段音频                     │
│                     └──► LLM推理（一次性）                  │
│                              └──► 生成完整回复              │
└─────────────────────────────────────────────────────────────┘

Omni-Flow（流式时间片）:
┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐
│ 片0    │  │ 片1    │  │ 片2    │  │ 片3    │  │ 片4    │
│ 0-200ms│─►│200-400ms│─►│400-600ms│─►│600-800ms│─►│ ...   │
│        │  │        │  │        │  │        │  │        │
│ 视频帧 │  │ 视频帧 │  │ 视频帧 │  │ 视频帧 │  │ 视频帧 │
│ 音频块 │  │ 音频块 │  │ 音频块 │  │ 音频块 │  │ 音频块 │
│   +    │  │   +    │  │   +    │  │   +    │  │   +    │
│ LLM推理│  │ LLM推理│  │ LLM推理│  │ LLM推理│  │ LLM推理│
│ "今天" │  │ "天气" │  │ "真的" │  │ "很好" │  │ ...    │
└────────┘  └────────┘  └────────┘  └────────┘  └────────┘
```

| 维度 | 传统架构 | Omni-Flow |
|------|---------|-----------|
| 触发方式 | VAD 检测说话结束 | 固定频率时间片 |
| 输入模式 | 完整一段话 | 增量感知包 |
| LLM 推理 | 一次性长推理 | 高频短推理 + KV Cache 复用 |
| 打断支持 | 不支持（要等说完） | 原生支持（软/硬打断） |
| 语音输出 | 整句合成后播放 | TAIL 流式跟读 |

# 七、写在最后

MiniCPM-o 4.5 最值得关注的不只是 9B 参数跑出了接近 Gemini 2.5 Flash 的效果，而是它在**交互范式**上的探索：

- 用 Omni-Flow 的时间片机制，把"回合制"变成"流式感知"
- 用 TAIL 方案，把"整句合成"变成"跟读式输出"
- 用 KV Cache 的增量更新 + 模态感知滑动窗口，在 12GB 显存上支撑持续运行

这些设计让 AI 从一个"你问我答的工具"变成了"持续在场的助手"。这对于智能座舱、无障碍辅助、具身智能等需要**持续感知和主动介入**的场景，意义远大于参数规模本身。

如果你也在做端侧多模态或实时交互相关的工程，Omni-Flow 的这几个设计——**异步流水线、时间片打包、模态感知的 KV 管理**——可以直接借鉴到系统架构里。
